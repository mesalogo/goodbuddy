### 数据与性能

- SQLite 合成库包含 10 个项目、1,000 个实体、10,000 个事件和 10,000 条事件实体关联。候选 ID 与排序逐项一致，数据计数不变、外键检查为空、完整性为 `ok`。真实 Host 事件另外通过生产数据库与批处理器写入：OpenCode 45 条／23 个 checkpoint，Continue 16 条／8 个 checkpoint，重放去重通过。
- 激活项目隔离后，测量发现原相关子查询较慢，改用实体集合查询。三轮各十次项目查询，旧 SQL 合计 3,517／5,302／4,190 ms；新 Worker 路径含传输为 39.18／34.01／36.04 ms。120 事件归属事务为 6.63 ms。此结果仅适用于该合成库 SQL 对照，见[监督后端证据](../features/conversation-supervision/progress.md#2026-10-05-后端阶段审查-a03a04a05)。
- Windows Electron 使用 2,000／10,000 条合成消息，原版与首次修复各三轮交替运行；后续缓存修正又做三轮对照。最大采样挂载量均为 15 个消息行、926 个 DOM 元素，展开、键盘、焦点、选区和滚动回归通过。缓存修正后的导航中位数为 38.5～39.1 ms，含聚焦后的两帧等待，不能作为纯渲染耗时或整体预算结论。
- 未操作导航后缓存条目为零；13 条消息交互后保留 38 条用户覆盖项，删除消息后归零。该测量统计缓存条目，没有测量堆字节。方法、每轮数据及原有滚动回归见[前端验证](../features/application-tool-navigation/progress.md#2026-10-05展开状态缓存复查)。

## 验证边界

本轮未做真实 Telegram／钉钉平台收发或付费图片生成，A06 验证的是生成完成后的生产交付契约。未做 macOS、Linux arm64、低端机节流、完整 App 性能预算或签名包安装验收，也未用用户生产大库证明性能。上述已测场景未观察到功能或性能退化，不能推广为所有设备和数据规模的保证。远程修复生效需要部署包含当前源码的 Agent；本轮没有提交、打包发布或升级用户安装。
